## 1. 引言

### 1.1 编写目的
本文档定义「投广管理客户端」的产品需求、功能边界、非功能指标与验收标准，作为后续概要设计、详细设计、开发、测试与验收的唯一需求基线。读者对象为：甲方（需求方）、乙方开发与测试人员、后续运维人员。

### 1.2 项目背景
本项目为仿照「龙豪软件 · 投广管理（百应工作台）」开发的电商投广运营工具，服务于抖音电商投广场景。核心目标是**实现「百应选品 → 视频下载 → 图转视频 → 抖音发布 → 千川发布素材」的全流程自动化**（**R17 修订顺序**），并提供多账号矩阵管理与分级授权能力。

业务主流程（**全流程自动化**）：

> 百应自动选品 → 解析并下载视频 → 去水印 / 转码 / 批量入库（**网页素材**）｜ 商品详情图片抓取 / 录屏 → 图转视频（**图转视频素材**）
> → **自动发布到抖音账号**（发布**商品详情图转视频**）→ **在巨量千川发布素材**（发布**网页下载素材**）　**【R17 修订】**

部署与权限：由**管理端**统一管理，**管理端可授权下游（客户端）的使用时长**；客户端按授权有效期运行。

## 2. 总体描述

### 2.1 产品定位与目标
一款面向**抖音电商投广运营人员（商家/投手/素材运营）**的运营工具，围绕「选品—素材—投放管理」提供一体化能力。目标：
- 将商品视频的采集、清洗（去水印/转码）、归档流程标准化、批量化；
- 将千川素材与违规素材的巡检、清理流程集中操作；
- 支持企业内多人员协同使用（本地/内网部署）；
- 降低人工重复操作，提高素材准备与投放运营效率。

### 2.2 产品范围
**范围内**：模块 A（百应工作台）、B（素材与工具）、C（千川管理）、D（投放看板）、E（视频处理引擎）、F（系统基础）；模块 **G（账号管理）、H（发布与计划）、I（选品与素材设置）、J（商品详情录屏）、K（授权与权限分级）** 为依据参考软件对照与甲方新增需求加入，**优先级待甲方确认**（见附录 F）。**抓取平台范围（R18）**：**抖音、快手、小红书、今日头条、拼多多、淘宝六平台全部纳入需求范围**，实施策略为「**可实现的先做、不能实现的待定**」（见附录 A / A-23、A-30）。

**范围外**：
- **淘宝/拼多多平台抓取**：已纳入需求范围，但**实施待 POC 评测后决定**（反爬最强、基本无法取得无水印源；未通过 POC 者不写入本期验收基线，见附录 A / A-23、A-30）；
- **视频画质修复（超分）不纳入本次交付范围**（见附录 A / A-06）；
- **AI 修补式去水印（inpainting）不纳入本次交付**，列为后续可选（见附录 A / A-03）；
- 不提供任何绕过平台资质、伪造交易数据的能力。

### 2.3 用户角色与特征
| 角色 | 特征 | 主要诉求 |
|---|---|---|
| 投广运营（主用户） | 熟悉抖音电商后台，非技术人员 | 快速查询商品视频、批量下载、素材归档 |
| 素材运营 | 负责素材生产 | 去水印、转码、裂变、查重 |
| 投放管理 | 负责千川账户 | 广告列表、计划、违规素材清理 |
| 系统管理员 | IT 运维 | 部署、账号/权限、路径与参数配置、日志 |

### 2.4 运行环境
- **客户端**：Windows 10 / 11（x64）。
- **部署场景**：企业本地/内网部署，**20 台 Windows 客户端使用**，采用**集中式架构**（1 台中心服务端 + N 台客户端）。媒体处理在客户端本地完成；中心库只存元数据与缩略图，视频文件存客户端本地，共享通过「素材仓库引用」实现。**详见附录 G 部署方案**。
- 依赖本地能力：本地文件系统读写、浏览器内核（登录态与取数）、本地 FFmpeg 视频处理；如涉及画质修复需 GPU。

### 2.5 设计与实现约束
- 交付形态：Windows 桌面客户端。
- 技术栈：
  - 客户端：**Electron + Vue3 + TypeScript**（UI、内置浏览器登录态、本地文件操作）；
  - 处理引擎：**Python**（`yt-dlp` / `FFmpeg` / `OpenCV` / `Playwright`）作为客户端伴生进程，负责多平台抓取、去水印、转码、裂变、查重；
  - 服务端（集中式部署）：**Spring Boot + MySQL + Redis**，负责统一账号/权限、任务调度、素材元数据、违规管理记录与日志。
- 第三方开源代码复用须遵守许可证（见 NFR-13 与附录 E）。
- 所有操作必须使用**用户本人已登录账号**的合法凭证，不得内置他人账号共享。

### 2.6 假设与依赖
- 依赖抖音百应/千川网页端可正常访问，页面结构可能变化（见 R-01）。
- 依赖甲方提供可登录的测试账号用于联调；终端须可访问百应/抖音所需域名，内网受限时需提供代理（见附录 A / A-17）。
- 依赖第三方平台开放能力/接口的可用性。

布局对齐参考软件：顶部菜单（百应工作台 / 商品查询）+ 左侧导航（投放看板 / 素材与工具 / 千川管理）+ 主工作区 + 底部状态栏（素材库读取数、记录数、当前下载目录）。

### 5.2 软件接口
| 接口 | 对象 | 说明 |
|---|---|---|
| IF-01 | 百应 | 商品查询、视频信息、视频源地址 |
| IF-02 | 抖音 | 视频链接解析、无水印源获取 |
| IF-03 | 巨量千川 | 账号、素材、违规素材列表与删除 |
| IF-04 | 小红书 / 快手 | 视频抓取（仅抓取，不发布） |
| IF-05 | 本地 FFmpeg / yt-dlp | 下载、转码、处理 |

### 5.3 硬件接口
本地磁盘（下载/素材库目录）、可选 GPU（画质修复）。

## 6. 数据需求与存储规范

### 6.1 主要数据实体
商品、视频、素材、下载任务、千川账户、违规素材记录、登录态凭证、操作日志；集中部署另含：用户、角色、权限、任务调度记录。

### 6.2 存储规范
- 本地库：SQLite（客户端轻量存储）；集中部署时中心库用 MySQL。
- 中心库只存**元数据 + 缩略图**；视频文件存客户端本地，共享通过「素材仓库引用」实现。
- 目录结构：`{根目录}/{账号}/{日期}/{商品ID}/`
- 文件命名：`{商品ID}_{视频ID}_{序号}_{时间戳}.{ext}`
- 状态栏显示「当前下载目录」，支持「设置下载目录」修改。
- 存储位置：优先 **D 盘**。

## 附录 D. 视频抓取可行性分析

**结论：技术上可行。** 抖音网页视频可抓取，并可通过通用引擎扩展至小红书等平台。

### D.1 抖音抓取技术路线
1. **SSR 数据提取**：抖音分享页/视频页会注入 `window._ROUTER_DATA`，其中包含视频元数据与播放地址。
2. **无水印转换**：带水印的 `playwm` 与无水印的 `play` 可互换，据此直接得到无水印源，无需裁剪，画质无损。
3. **反爬绕过**：移动端 User-Agent + 完整请求头（UA / Referer / Cookie）可绕过部分反爬；部分接口需 `X-Bogus` / `a_bogus` 签名，算法随平台更新，需持续维护。
4. **成熟工具链**：`yt-dlp` 原生支持 Douyin / TikTok 等站点，社区高频维护，可作为基础引擎。

### D.2 多平台扩展
- `yt-dlp` 支持上千个站点，可覆盖 B站 / YouTube / TikTok / 今日头条 等；
- **今日头条**（字节系）、**快手**纳入本期内；**小红书**需自研解析器或接入第三方 API（仅抓取、不发布）；
- **淘宝 / 拼多多**反爬最强、且基本无法取得无水印源，**实施待 POC 评测后决定**（见附录 A / A-23）；**R18：六平台（抖音 / 快手 / 小红书 / 拼多多 / 今日头条 / 淘宝）全部纳入需求范围，可实现的先做、不能实现的待定**；
- 抓取层采用 **extractor 适配器模式**，平台与核心引擎解耦。

### D.3 兜底方案
若自研抓取受限，可接入商用数据 API（如 Apify / TikHub，按量计费）作为兜底通道。

### D.4 风险提示
反爬升级（R-01/R-03）、签名失效、版权与平台条款限制（R-02）。

## 附录 G. 部署方案（1 台服务端 + 20 台客户端）

### G.1 总体架构

```
        ┌────────────────────────────┐
        │   中心服务端 × 1（内网）      │
        │   Spring Boot + MySQL + Redis │
        │   账号/权限 · 任务调度 · 元数据 · 日志 │
        └──────────────┬─────────────┘
                       │ 内网
        ┌──────────────┴─────────────┐
        │   客户端 × 20（Windows）      │
        │   每台 10 个抖音账号          │
        │   Electron + Vue3 + Python  │
        │   抓取 · 去水印 · 转码 · 下载 · 素材库 · 自动发布 │
        └────────────────────────────┘
```

### G.2 组件职责

| 组件 | 职责 | 不承担 |
|---|---|---|
| 中心服务端 | 统一账号与权限、任务调度、素材元数据、违规记录、操作日志 | **不存视频文件、不做媒体处理** |
| 客户端 | 抓取、去水印、转码、下载入库、素材库、自动发布 | 不存全量业务数据 |
| **发布专用机（建议 1–3 台）** | **常驻开机**，承载需定时发布的账号登录态，执行定时自动发布 | — |

### G.3 服务端规格建议
- CPU 8 核 / 内存 16G / SSD 256G 起（元数据量小，主要吃并发与连接数）
- MySQL 与 Redis 可与应用同机部署；**约 20 客户端**规模足够
- 若日处理量上升，可先水平扩展应用节点

### G.4 客户端规格建议
- Windows 10 / 11（x64），**4 核 / 8G 内存 / 可用磁盘 ≥ 100G**（素材本地存储）
- 转码吃 CPU；如需后续 AI 能力（画质修复/修补去水印）建议配独显
- **安装包与运行库占用**：一体化安装包（见 A-24）含 Electron + Python 引擎 + FFmpeg + 浏览器内核（Chromium），安装包体积约数百 MB~1GB+；首次运行需完成内核初始化 / 依赖自检

### G.5 账号与登录态（关键）
- 账号**元数据**存服务端；**登录态（Cookie）本地加密存储**，不做跨机共享
- 建议**账号与机器绑定**：一个抖音账号固定在一台机器上登录，避免登录态冲突与风控

### G.6 定时发布怎么保证（关键）
- **已定口径（A-20）：每台机器各自上传**，**不设集中发布机**。
- 已知代价：机器关机期间的定时任务**会漏发** → 必须配套**离线补偿**：默认「**顺延补发**」（错过的任务开机后补发，跳过/顺延可配）。
- 落地要求：客户端内置定时调度（FR-H5）；建议关键账号所在机器尽量常开；发布脚本实现排期见 A-25（本阶段待定）。

### G.7 网络要求
- 客户端与服务端在内网互通
- 客户端须可访问外网：抖音、百应、千川所需域名；内网受限时需提供代理
- 出口 IP 建议分散，避免集中触发平台风控（见 R-08）

### G.8 部署与升级流程
1. **服务端**：内网服务器安装（提供部署手册 + 一键脚本）
2. **客户端**：打包为**一体化安装包**（EXE/MSI，含 Python 引擎 + FFmpeg + 浏览器内核，见 A-24），内网分发（可域推送）；安装后配置服务端地址、首次运行完成内核初始化 / 依赖自检
3. **升级**：客户端自动更新，或重新分发安装包

> **安装包构成清单**：Electron 主程序 / Python 运行时（PyInstaller 打包）/ FFmpeg 二进制 / Chromium（Playwright）/ OpenCV 依赖。内网无外网时，浏览器内核等须**随包预置**，不可依赖首次联网下载。

### G.9 存储与容量
- 视频文件全部在客户端本地：按「每台日产出 × 保留周期」估算磁盘需求
- 建议提供**素材保留策略**与磁盘清理提醒，避免打满

### G.10 运维
- **日志**：客户端关键操作上报服务端，集中查看
- **监控**：任务成功率、失败原因 Top N、客户端在线数
- **排查**：提供一键导出诊断包

### G.11 发布吞吐测算与排产（20 台 × 10 账号 · R16-3）

### G.12 产能扩展与扩容策略（R16-3）

**基准口径：每台客户端承载 10 个抖音账号**（`20 台 × 10 = 200 账号`）。

**单账号每日工作量**（按当前配额）：
- 千川素材：每账号 5 品 × 每品 10 条 = 50 条 × 0.5–1 分钟 ≈ 25–50 分钟
- 抖音发布：每账号 5 条 × 1.5–2 分钟 ≈ 7.5–10 分钟
- 合计 ≈ **0.5–1 小时/账号/天**

**每台承受能力**：

| 每台账号数 | 单台日占用 | 可行性 |
|---|---|---|
| 5 个 | 2.7–5 小时 | ✅ 轻松 |
| **10 个（基准）** | **5.4–10 小时** | ⚠️ 需机器常开 |
| 20 个 | 10.8–20 小时 | ❌ 近 24h，风控高 |
| 50 个 | 27–50 小时 | ❌ 物理不可能 |

**扩容四类手段（按推荐度）**：

| 手段 | 说明 | 适用 |
|---|---|---|
| ① **加机器**（首选） | 机器数 ≈ 账号数 ÷ 每台账号数；账号与机器绑定（G.5），避免登录态冲突与关联风控 | 规模线性增长 |
| ② 提高每台账号数 | 5 → 10 可行；20 逼近 24 小时且同机多账号关联风险大 | 空间/预算受限时 |
| ③ **千川改开放平台 API** | 批量上传，单条由「分钟级」降到「秒级」，每台承载可提升数倍（见附录 H） | 规模上 500+ 时优先 |
| ④ 降配额 | 「每品 10 条」等配额本就可配 | 产能临时不足时 |

**机器数对照（每台 5 / 10 账号）**：

| 目标账号数 | 每台 5 账号 | 每台 10 账号 |
|---|---|---|
| 200（当前基准） | 40 台 | **20 台** |
| 500 | 100 台 | 50 台 |
| 1000 | 200 台 | 100 台 |

**约束与前提**：
- **风控**：每台独立出口 IP / 代理 + 错峰发布（R-08 / R-12），否则规模越大越易被平台关联
- **服务端**：中心只存元数据 + 缩略图 + 心跳（G.2），100 → 数千账号时单机足够，必要时水平扩展应用节点（NFR-11）
- **磁盘**：单台约 5GB/天（以千川素材 500 条 × 10MB 计），需配套素材保留与清理策略

### H.1 注册成为开发者
1. 访问巨量引擎开放平台（open.oceanengine.com），点右上角「注册」
2. 已有巨量引擎账号可直接登录
3. 点「注册为开发者」→ 填写企业信息 → **完成企业打款认证** → 签订合同
4. 在「账号信息」页面激活接收通知的邮箱

**限制**：一个公司信息**仅能注册认证一个开发者账户**；建议用公司邮箱注册。

### H.2 创建应用（获取 APPID / Secret）
1. 「应用管理」→ 创建应用，选择业务场景：**巨量营销** 或 **巨量千川**（每个场景最多 10 个应用）
2. 填写：应用名称（2–50 字）、应用图标（建议 72×72、<1MB）、**回调地址**、**申请权限（scope）**
3. 提交后 **1 个工作日内审核**；通过后获得 **APPID + Secret**

### H.3 申请客户授权（OAuth 2.0）
1. 在应用基本信息页取得授权 URL 模板，拼装参数：
   - `app_id`：应用 ID
   - `state`：自定义参数（回调原样返回，可用来标识客户）
   - `scope`：权限范围（不能超出应用已拥有权限）
   - `redirect_uri`：回调地址，**必须与设置的回调地址一致**
2. 把授权 URL 发给**业务账户管理人**，由其登录并勾选账户、点击「同意授权」
3. 授权成功后回调地址会收到 `auth_code`
   - ⚠️ **auth_code 有效期仅 10 分钟，且只能使用一次**

### H.4 换取 Token 并调用
1. 用 `auth_code` 换取 **Access Token（默认有效期 1 天）** 与 **Refresh Token（默认 30 天）**
2. 用 Access Token 调用接口；失效后用 Refresh Token 刷新
   - ⚠️ 刷新会同时作废旧的 Access/Refresh Token，需妥善存储

### H.5 对本项目的关键前置条件
| 项 | 说明 |
|---|---|
| 主体资质 | 需企业营业执照 + 打款认证 + 签合同（个人无法申请） |
| 回调服务 | 需自建一个可接收回调的地址（可挂在中心服务端） |
| 千川可授权账户类型 | 抖店店铺管理账户 / 方舟代理商管理账户 / 纵横旧版巨量引擎工作台管理账户 |
| 授权数量 | **默认可授权 50 个账号**，不足需提工单（上限约 500） |
| 接口范围 | 是否存在「删除素材」类接口需在千川 Scope 文档中确认；若无，Browser 自动化仍是兜底 |

### H.6 结论
取得凭证需要**企业资质 + 审核周期**（通常数天至数周），且**不保证有「删除素材」接口**。
因此本项目策略为：**先做浏览器自动化（可立即开工），API 作为后续优化**。

## 附录 I. 权限字典（原子权限项 · R18 初版）

> **用途**：定义「账号与权限分级」（A-16 / FR-F5-01 / FR-K1-03）的**原子权限项清单**。本清单为**初版基线**，**可增删**。
> **模型**：`权限项 = 原子 key`；**授权 = 层级（代理层级）× 职能（管理员 + 运营 + 只读）**；矩阵与字典**均配置化**（代码只认 key）；判定由**服务端强校验**，前端仅隐藏 / 置灰。
> **状态**：⏳ 待甲方**补充（增删）**并**划分各级权限归属**（「层级建议 / 职能建议」两列为乙方初步建议，可覆盖）。
>
> **标准写法（R24 统一：全表唯一口径，不得混用）**
>
> | 列 | 标准枚举值 | 含义 |
> |---|---|---|
> | 层级建议 | `全部层级` | 总管理员 + 各级代理 + 终端客户端（所有人） |
> | | `总管理员` | 仅总管理员 |
> | | `总管理员 + 各级代理` | 总管理员与各级代理（**不含**终端客户端） |
> | | `上级层级` | 当前账号所在层级之上的各层级（含总管理员） |
> | | `终端客户端层` | 仅终端客户端（最末级） |
> | 职能建议 | 单一职能三选一：`管理员`、`运营`、`只读` | 仅一种职能 |
> | | `管理员 + 运营`（同式） | 多职能取**并集**，用 `+` 连接 |
> | | `全部` | 管理员 + 运营 + 只读（三种职能全含） |
>
> **书写规则**：① 多值一律用 **`+`**（并集），**禁用 `/` 与 ` · `**；② 层级与职能**各按上表取值**，不自造新词；③ 权限项内描述文案可用 `/`（如「新增 / 编辑 / 删除」），但**层级 / 职能两列不适用**。

## 需求变更补充记录：A-104（2026-10-28，覆盖旧 A-65 / FR-I5-01 冲突条文）

1. **来源边界**：自动选品仅读取百应热点趋势、联盟榜单等已启用来源在当前页面已显示的商品；不翻页、不搜索、不遍历全部类目，也不回退到选品广场或其他商品池。来源中的商品直接形成候选，按商品 ID 去重。
2. **自动推荐与执行**：系统用当前可见商品的评分，按高分商品数降序、平均分降序推荐重点末级类目，并自动分配商品、自动加车；不要求用户手选商品或类目。子类目优先在不同账号间错开，候选不足允许跨账号复用。
3. **强制去重**：20 台电脑上全部账号共用一个商品 ID 全局唯一登记；每个账号已选过的末级类目永久排除，同一账号同一轮每个末级类目最多加一件。账号以稳定抖音号 ID 标识，不使用本机数据库行号。
4. **并发和不确定结果**：客户端在发出百应加车命令前，必须向轻量共享登记服务原子预留商品 ID 与账号末级类目；服务不可用、候选预留失败或身份缺失时不发送加车命令。确认加车成功后提交登记；明确未加入则释放；结果不明则保持占用并进入人工核查，不自动解锁或重试。
5. **历史迁移与部署前提**：首次开放选品前须汇总 20 台电脑已有商品 ID 并导入共享登记服务。旧本地库不能还原历史末级类目，因而只能导入商品 ID；历史类目约束从服务启用后新成功登记的数据开始。服务主机、私网 HTTPS 地址、证书与访问密钥由甲方网络环境提供。
6. **实现状态**：原型 v1.44 已验收。工程代码已加入当前可见来源候选、类目自动推荐、客户端登记接入和 Spring Boot/MySQL 共享服务；类型检查与 Python 语法检查通过，服务端 `mvn -B -DskipTests package` 构建通过。百应真实页面字段/加车流程仍待实页验收；未连接百应、未部署服务、未导入生产数据或启动真实加车。
