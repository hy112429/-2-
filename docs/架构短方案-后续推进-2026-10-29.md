## 1. P0 / P1 / P2（推进顺序）

### P0 — 堵住「假无货 / 错加车」风险（先验收、后扩量）

1. **A-105 只读预览验收**（逐账号「预览候选」，**不加车**）  
   - 验收三源独立统计、广场可不依赖热点/联盟命中、通用模式未知类目可展示、品类模式未知类目排除、统一分与前 3 个商品 ID。  
   - 产出：`diagnostics\selection\priority-sources\*`、类目报告、界面计数截图/日志。
2. **A-105 正式批次 · 仅落候选计划**（跨账号统一分胜出 / 同分先占用；**建议本阶段仍不加车或仅 1 账号 1 品加车**——见 C-1）  
   - 验收：同一商品 ID 全批最多分给一账号；败选有原因；计划可从 DB/选品过程日志回读。
3. **联盟来源商品 → 计划驱动加车小流量复验**  
   - 衔接 Step 12 加车：标题定位卡片 + `m_add_card` 确认；失败不占配额。  
   - 明确：**联盟榜单是候选来源之一，不是另一套加车栈**。

### P1 — 稳定多账号与发布半自动

1. 多账号正式批次端到端（本机互斥 + 配额 + 恢复批次策略按 A-105 旧检查点规则）。  
2. Step 12-B Step 4：真实退出恢复 / 低频稳定性。  
3. 发布队列接入图转视频产物与自动发布（业务若优先可与 2 并行，但不得挤占 P0）。  
4. 技术债启动设计（仍先方案后代码）：Schema 多入口收敛、`browser_cdp.py` 拆分与白名单边界、打包 `tg_pkg_staging` 与仓库 `engine/` 同步检查单。

### P2 — 外部依赖与规模化

1. 共享选品登记服务回切（20 机商品 ID 全局唯一）——等甲方主机/HTTPS/密钥。  
2. 千川开放平台正式 API（等 AppID/Secret/Token）。  
3. 罗盘探针②~⑥（用户曾收缩为仅登录入口）。  
4. 安装包版本展示一致化、脏工作区收口策略。
