# 选品商品 ID 批量去重方案与实施记录

更新日期：2026-11-10

## 目标与范围

多账号选品共用一套本机商品 ID 防重登记。候选池生成后，按本轮候选 ID 查询历史记录和发布队列；同一批账号共用一份查询结果；同一商品仍只允许一个账号获得最终预留。优化只改变本机查重和跳过日志的访问方式，不修改百应筛选条件、评分规则、账号分配优先级或平台页面操作。

## 精确处理流程

1. 每个账号完成只读候选采集和本地配额读取，最多保留约 200 个候选，不先逐账号启动历史查重进程。
2. 将有效账号的候选 ID 与末级类目 ID 一次通过标准输入提交给本机登记命令。命令校验账号键唯一，将所有候选 ID 合并去重，按 SQLite 参数上限分块执行 `IN` 查询；类别用量也只聚合本轮候选涉及的类目。
3. 历史商品表、加车配额事件和升级前仍有效的发布队列只做一次兼容导入，结果存入带商品 ID 主键的本机登记表，并以迁移标记避免后续轮次重扫历史。发布队列每轮仍按候选 ID 做有限查询，以发现升级后新建的任务。
4. 账号级发布队列锁定查询也增加候选 ID 参数；空候选不启动查询进程。数据库为发布队列商品 ID 和账号/商品组合建立索引。
5. 过滤后的账号候选仍交给原有跨账号分配器处理；被一个账号占用的 ID 不会再分给同批其他账号。
6. 真正加车前继续在 SQLite `BEGIN IMMEDIATE` 事务中校验并原子预留商品 ID、末级类目。事务会重新检查活动登记与活动发布队列；读写失败或返回不完整时中止该账号，不放行。
7. 每批重复/互斥跳过明细通过 `append-batch` 一次写入一个 SQLite 事务。日志保留每条商品 ID、标题和原因；任务摘要展示总数与最多 3 个示例。

## 容错边界

- 候选批量快照缺失账号结果、数据库异常或 JSON 返回不完整：停止当前批次的后续选品，不按“没有重复项”继续。
- 最终预留仍是并发保护的最后一道检查；预览结束后被其他本机任务预留的商品会在正式预留时被拒绝。
- 只读预览和查询不触发百应加车。平台页面选择、加车和发布操作流程未在本次改动中触发。
- 旧历史首次导入会读取一次既有 ID，可能比后续轮次慢；迁移成功后按候选 ID 增量查重。

- 已实现：历史商品、加车事件、有效旧发布队列的一次性兼容迁移与索引；发布队列候选 ID 有限查询。
- 已实现：正式预留中的批量预读和原子事务保护；队列命中与登记命中均阻止加车。

## 2026-11-11 选品候选随机轮换与补位

### 方案

1. 每个账号仍只从当前百应可见商品中采集，候选池上限为 200 个；不扩大账号范围，也不放宽已保存的类目、屏蔽词、数据阈值和每日配额条件。
2. 在本机登记批量快照、发布锁和配额过滤完成后，才对剩余合格商品做加权随机排序。候选综合分越高，被排到靠前位置的概率越高，但不再每轮固定从同一批最高分商品开始。
3. 使用选品批次 ID 与商品 ID 生成稳定随机键。同一批次恢复或重新准备候选时顺序稳定；新批次使用新 ID 重新轮换。
4. 多账号仍共用同一批商品 ID 互斥分配集合。人工在预览中勾选的商品继续按原手动路径处理，不会被自动随机替换。
5. 自动模式为每个有剩余配额的账号保存最多 50 个已筛选、已去重并已做跨账号分配的候选快照。当前实际目标商品数仍由用户设置和每日配额控制；50 只是原子预留遇到并发冲突时的补位池。
6. 主进程按候选顺序逐个尝试 SQLite 原子预留；商品被另一任务抢先登记时跳过该项并检查后续候选。平台操作开始后结果不明仍保持待核查，不自动释放或再次上传。
7. 进度百分比只表达流程阶段完成度；批次结束时另显示实际确认加入选品车的商品数，防止“流程 100%”被误读成“选到了商品”。

### 实施记录

- 已实现：在 `selection_candidates.ts` 增加由批次种子驱动的加权随机排序；只对硬筛选、本机登记、发布锁和配额过滤后的自动候选生效。
- 已实现：跨账号分配器优先沿用批次随机键，并继续按同一商品唯一分配；人工勾选候选保留原分数顺序和手动流程。
- 已实现：自动候选计划由原目标数三倍扩大为最多 50 个备用候选；主进程最终原子预留遇到冲突时可继续向后补位。
- 已实现：选品终态单独显示本批次已确认加车数，并注明进度百分比代表步骤进度。
- 验证通过：Node 主进程 TypeScript 检查、Vue/渲染层类型检查、Electron Vite 生产构建和 `git diff --check`。
- 未执行：自动化测试及百应真实平台验收。当前构建成功不代表百应实机选品已通过；需要新批次观察候选轮换、冲突补位和实际加车数。

## 2026-11-11 虚拟滚动来源页失败修复

### 已确认原因

10:54 批次的百应来源采集、候选评分、本机登记和候选分配均已完成。失败发生在“加入选品车并取回商品 ID”前的来源页复核：热点趋势页面使用虚拟滚动，只在当前窗口渲染少量商品；旧执行器要求备用候选组的所有商品 ID 同时出现在当前 DOM，60 秒内无法满足，于是把页面未渲染误判为整批无法安全定位。此次错误由候选备用池扩大后暴露，平台没有收到这些未复核候选的加车点击。

### 修正

- 来源页复核改为每个候选独立处理：在真实滚动容器中寻找候选，找到后再按商品 ID 唯一定位。
- 当前候选在有限滚动窗口内未渲染时，只生成“未点击加车、跳过当前候选”的结果并继续备用候选；不再因为虚拟列表不能同时显示全部候选而整批失败。
- 已发出加车请求但回执不明、账号登录/浏览器连接异常、限流或人工验证仍按原安全规则保留待核查并暂停，禁止盲目重试。
- 修复只针对来源页候选复核，不放宽商品 ID、账号归属、筛选质量和本机原子登记校验。

### 本次故障处理结论

该批次的 0 个确认加车不是商品被平台拒绝，而是客户端在点击前等待 60 秒后安全停止；本机预留已按待核查规则保留，不能直接重复选品。修复后需新建测试批次验证热点趋势、联盟榜单和选品广场三种来源的滚动定位结果。
