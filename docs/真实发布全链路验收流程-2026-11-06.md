# 真实发布全链路验收流程

更新：2026-11-06。适用范围：Step 16 抖音发布、Step 17 千川素材上传、Step 18 定时调度、Step 19 回执与重试，以及“抖音发布成功后下载商品视频并上传千川”（P-33 路径 A）。本文件是**验收操作单**，不是已通过报告。实际进度以 [TODO.md](TODO.md) 为准。

## 1. 先确认“已经成功过一次”证明了什么

请先在「发布队列」和相应平台核对那次成功记录，并把结果填入文末记录表。**上传视频成功**只证明文件传到投稿页；**提交审核**只证明平台收到了投稿；只有平台作品页和队列都能确认 `published`，才算该商品的抖音发布成功。千川素材上传还要单独核对目标千川账户中的远端素材 ID。

已有记录可以计入对应测试用例，条件是能确认客户端版本、抖音账号、商品 ID、视频文件、队列 ID、操作时间、平台结果，以及没有重复作品。若只有口头“成功”或截图缺少账号/商品/时间，记作“已有成功线索，待核实”，不为了补证据立即重发。已有 #42 是一次 `published` 回执的线索；它关联的 #56/#57 为 `detail_generated`，不能用于 Step 17 网页素材上传验收。旧待核查队列 #38/#39 不纳入本轮，也不要清除其状态。

### 测试类型与现有覆盖

本操作单 **P01–Q04 主要是黑盒测试**：按用户可见界面和真实平台结果判断功能是否有效。再读取队列状态、事件、截图和日志核对内部过程时，属于**灰盒核查**。白盒测试是针对源码分支、状态机和边界的单元/隔离测试；它不能代替真实平台回执。

| 类型 | 已做的部分 | 尚缺的部分 |
| --- | --- | --- |
| 白盒/隔离测试 | 2026-11-06 发布专项回归通过：Python 110 项、Step 17 素材归属 5 项、桌面 3 项及 P-33 隔离脚本。补修后全仓 Python 310/310、桌面 51/51，客户端构建通过。详见 [白盒测试报告](真实发布白盒测试报告-2026-11-06.md)。 | 未量化全分支覆盖率，真实平台结果无法由模拟证明。 |
| 黑盒/真实平台测试 | 已有 #42 一次抖音 `published` 记录；用户另反馈一次“真实上传成功”，仍需核实它对应抖音投稿、作品发布还是千川素材。 | 本操作单列出的手动/自动/定时、失败恢复、两条千川素材及发布后自动编排尚未逐项有完整平台证据，不能宣称全链路黑盒通过。 |

所以当前结论是：**现有全仓自动化白盒回归通过，黑盒测试只有待核实的单点成功线索；真实全链路仍未验收通过**。执行下文用例时，优先复用已有可核实证据，缺失的失败边界可用隔离测试补足，不为制造异常而重复提交真实作品。

## 2. 什么才叫“全面通过”

| 层级 | 判定 |
| --- | --- |
| A. 抖音真实发布 | 专用账号上各有一条**手动准备后发布**和**新任务自动发布**的明确平台回执；同账号商品、视频、短标题/简介、购物车商品、封面和保存权限均与队列一致；不能把 `submitted_review` 当 `published`。 |
| B. 定时与回执 | 新计划到点启动、离线错过后顺延；失败截图、原因、事件和 CSV 可核对；结果不明不自动重发，明确未提交才可安全重试。 |
| C. 千川素材 | 同一抖音账号、同一已发布商品、已绑定千川账户的 **2 条真实 `web_download` MP4** 上传成功并取得不同远端素材 ID；断网、额度顺延、离线续行与提交前有限重试有证据。 |
| D. 发布后自动编排 | 只在 `published` 后按队列商品 ID 和账号 ID 下载网页视频并进入 Step 17；`submitted_review`、无视频、未授权、无绑定分别得到正确状态；重复触发不重复上传。 |

**完整链路通过**须 A–D 全部满足。当前若只验证 A，可标“抖音发布通过、千川/调度待验”，不要写“全链路通过”。Step 20 违规素材远端删除、Step 33 成功后隔 24 小时追加，以及跨电脑全局五账号组额度属于独立验收，不能并入本轮结果。

## 3. 测试前准备

1. **版本**：记下正在运行的客户端来源（源码开发版或安装包）、版本/构建时间和 Python 引擎实际加载路径。当前源码已通过类型检查与构建；旧 v0.0.10 安装包不含之后全部修复，不能用它证明当前源码通过。
2. **账号**：指定一个专用抖音测试账号，确认百应、创作者中心已登录且有商品分享/挂车和发布资格；再指定它已绑定、已登录的千川账户。若测试多账号隔离，再准备第二个账号，不能用同一浏览器登录态冒充。
3. **商品与素材**：准备一个账号选品车中可见、可带货且可发布的测试商品；记录准确商品 ID。抖音投稿使用该商品 Step 14 的 9:16 详情图转视频 MP4。千川使用同账号同商品、来源已确认的两条**不同**网页下载 MP4；核对文件存在、可播放、账号/商品归属。不要把图转视频改标为 `web_download`。
4. **任务与开关**：只新建并记录本轮测试队列 ID。手动和自动任务使用**两个不同商品**；已发布任务不能重复排期。先在「千川管理 → 发布成功后自动获取千川视频并加入 Step17」记录开关原值：测试手动 Q01 的商品时可暂时关闭，避免 P04 一发布就由 P-33 自动抢先入队；测试 P05/Q04 的另一个商品前开启，结束后恢复原值。开始前查看旧队列状态、当日配额、同商品锁和素材库，确认不会误领历史任务。
5. **控制范围**：先在「发布队列」开启“人工复核”，确认按钮显示“已开”；这样准备阶段会停在最终发布前。要测试真正全自动时，只对新建测试任务按既定设置执行，并确认关闭人工复核的提示。最终点击抖音“发布”、千川“提交”或测试远端删除前，操作人应当场核对指定账号和商品；不要将文档本身视为对任意旧任务的操作许可。
6. **证据目录**：在 D 盘建立本轮独立目录，例如 `D:\software\codex\publish-acceptance-YYYYMMDD\`。保存截图、导出的 CSV、队列/千川事件和 `ffprobe` 结果；截图遮住账号密码、Token、Cookie、手机号，不修改原始平台回执。记录各平台与 Windows 的时间，避免把旧截图算入新任务。

## 4. 执行顺序与预期结果

每个用例只操作记录表里指定的新任务。出现登录/验证码/资质问题时先记录并人工处理；出现“已经点击提交但结果不明”时停止该任务并去平台核对，**不点击重试**。

## 5. 判定与收尾

- **通过**：对应行有“客户端记录 + 远端页面/回执 + 时间/账号/商品一致”的证据；同一任务未出现第二次作品或第二个不应有的远端素材。只有明确 `published` 才能触发发布后编排。
- **待审核**：平台已受理但仍是 `submitted_review`，保留任务，待平台结果；不能算已发布，也不能启动 P-33。
- **待核查**：提交结果不明、远端 ID 不可确认或页面证据矛盾。暂停该任务的重试，写明待查点；其他任务是否继续按队列隔离规则观察。
- **阻塞**：账号未登录、验证码、权限/资质不足、没有合格 `web_download` MP4、千川绑定或授权缺失。写明缺什么，不通过伪造来源、改状态或使用别的账号的素材绕过。
- **不适用**：只在测试范围确实没有相应业务时使用，并写原因；不能把必测成功路径标“不适用”。

验收完成后关闭本轮测试新增的未执行计划，恢复人工复核和 P-33 开关的原值，确认旧队列状态没有改变；记录平台作品和千川素材的最终去向。**不要为了清理测试而直接删除平台作品、远端素材或本机审计记录**；是否删除测试资产另按账号所有者的实际操作范围处理。
