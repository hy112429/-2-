## 判断边界与改进顺序

- `11001` 在这些响应中的原始提示是网络不稳定；HTTP 层为 200，不能直接认定为限流，也不能因等待倒计时结束就判为恢复。用户的 Edge 手动成功反馈说明应比较浏览器、账号资料和请求行为；仍需同账号同商品 ID 的可比证据。
- 先用 B 电脑的已授权只读范围，分别记录 Chrome 托管资料与 Edge 独立资料的页面入口、`material_list` 脱敏请求字段（尤其 `search_text`、类目和筛选状态）、请求数量/间隔、HTTP/业务码、平台原文和请求追踪号。不要保存 Cookie、Token、签名或完整敏感响应。Edge 必须按 `account-{id}` 使用独立资料目录；不得把 Chrome 资料直接交给 Edge，也不得借用日常 Edge 资料来承担多账号自动化。
- 对已保存池中的商品，核对当前消费账号是否能从原来源页唯一找到同一商品卡片；再核对已验证的决策页是否存在当前账号可操作的加车入口。仅有详情成功不足以加车。若这两条官方页面入口均不能确认，加车前停下并保留商品检查点。
- 如采用人工接力，先由用户在正常可用的官方页面按当前账号处理指定商品；客户端随后必须从同账号选品车回读精确商品 ID、推广关系及必要详情，确认后才能登记 `cartAdded`，再继续素材和抖音发布。现有 `recoverExistingCart` 只接受此前已确认加车的检查点；人工加车回读是待设计/实现，不可直接把旧池标成已加车。此分支属于新流程，先按项目 `AGENTS.md` 澄清并获用户确认。
- 若页面问题仍不可归因，保留真实 11001 与检查点，按既定退避恢复；不能通过伪造平台响应、放宽筛选、复用其他账号加车结果或跳过详情来制造发布成功。
